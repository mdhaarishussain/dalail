# CLAUDE.md — Dalail

Dalail is an offline-first mobile app that helps Sunni Muslims (Ahlus Sunnah wal Jama'ah, followers of Imam Ahmad Raza, all four madhabs) answer objections in religious debates. A user types what the other side is saying (English or Roman Urdu); the app finds the matching objection and shows a scholar-verified rebuttal, the dalail (Quran ayat and hadith) supporting it, and the next likely objection with its answer. First topics: Tawassul and Istighatha.

Every session must follow the rules below. When this file conflicts with anything else in the repo (including `apps/mobile/AGENTS.md`), this file wins.

## Non-negotiables

1. Never author religious content. Do not write, paraphrase, translate, or "fill in" Quran text, hadith text, translations, gradings, rebuttals, scholar names, or citations from your own knowledge — not in fixtures, not in tests, not in comments, not as "examples". All religious content comes only from the `corpus/` folder supplied by the project owner. Single exception — the ingestion workflow (Phase 3): you may extract and split owner-supplied article text into nodes (the extracted text must be a verbatim substring of the source, enforced by a checker), and you may write Roman Urdu search phrasings (`claim_roman_urdu`), because those are how users type questions, not religious content. Everything produced this way is `status: draft` until a scholar verifies it.
2. Fixtures must be obviously fake. Every placeholder string starts with `FIXTURE:` (e.g. `FIXTURE: claim text for tawassul node 1`). Fixture dalil references use the reserved collection `fixture` (e.g. `fixture:quran:1`, `fixture:hadith:1`) and resolve to placeholder text from `corpus/fixtures/`. The production build must refuse to bundle any `FIXTURE:` content (add a check).
3. Dalail are displayed verbatim. The app shows Quran/hadith text exactly as stored in the verified database, with its reference (and, for hadith, the grading where the scholar gives one). Nothing generated by an LLM is ever displayed as a verse, hadith, or scholar's words.
4. Only `status: verified` nodes are shown in the production build. Draft/under-review nodes appear only in a dev build behind a visible "UNVERIFIED" banner.
5. Fully offline. No servers, no analytics, no telemetry, no crash reporting that phones home. The only network call ever allowed is the optional one-time model download, started by the user.
6. The LLM is optional and never the source of truth. The app must be fully useful with the LLM disabled (retrieval-only mode). Any LLM-written text is labelled "AI summary — not scholar's words" and only summarises the retrieved node.
7. When unsure, ask the user instead of guessing. If retrieval confidence is low, show the top candidates ("Did you mean…?") rather than picking one.
8. Stop at the end of each phase (section 9), summarise what was built, list open questions, and wait for my go-ahead.

## Architecture

### Monorepo layout (pnpm workspaces for JS/TS, uv for Python)

```
/apps/mobile          React Native app (Expo + custom dev client, TypeScript)
/packages/core        Shared TS: types, retrieval, Roman Urdu normaliser, ranking
/pipeline             Python: validate corpus -> embed -> build SQLite DB
/corpus
   /nodes             Real markdown nodes (empty for now, owner supplies)
   /fixtures          FIXTURE nodes + fake dalil used in dev/tests
   /schema            JSON Schema for node frontmatter
/eval                 Test questions + eval runner (Node, uses packages/core)
/docs                 Architecture notes, decisions log (ADR-style)
```

### Stack

- App: React Native via Expo (current stable SDK) with `expo-dev-client` / prebuild (native modules required), TypeScript strict, Expo Router for navigation, Zustand for state, no UI kit lock-in (build a small component set).
- Database on device: SQLite with FTS5 + sqlite-vec via `@op-engineering/op-sqlite` (verify FTS5 and sqlite-vec support in its current docs; if either is missing, stop and report options before choosing an alternative).
- LLM + embeddings on device: `llama.rn` (llama.cpp bindings). LLM loaded from a downloaded GGUF; embedding model shipped in the APK or downloaded with the corpus.
- Embedding model: `multilingual-e5-small` in GGUF. The exact same model file is used in the pipeline (via `llama-cpp-python`) and on device, so vectors are compatible. Parity test: the same 20 strings embedded in both must have cosine similarity > 0.99. Use e5's required prefixes (`query: ` for user queries, `passage: ` for indexed text).
- Candidate LLMs (bake-off later, keep the model swappable): Qwen3-4B-Instruct Q4_K_M (front-runner), Gemma 3 4B Q4_K_M. Model metadata (URL, size, sha256, chat template, context length) lives in a single config file.
- Pipeline: Python 3.11+, pydantic, `python-frontmatter`, `llama-cpp-python`, `sqlite-vec`.

### Retrieval contract (implemented in `packages/core`, used by both app and eval)

```
query
 -> normaliseRomanUrdu(query)
 -> [optional, tier ≥ LLM] rewriteQuery()   // LLM -> canonical English, JSON-constrained
 -> keyword search: FTS5 bm25 over claim_en, normalised aliases, topic names
 -> vector search: sqlite-vec over alias + claim embeddings
 -> reciprocal rank fusion (k=60), aggregate by node id
 -> confidence = f(top score, gap to #2)
 -> result: { status: "match" | "ambiguous" | "no_match", candidates: [...] }
```

Thresholds live in config and are tuned via `/eval`. Never return a single "match" when the gap between #1 and #2 is small — return `ambiguous` with up to 3 candidates.

## Working style

- Small, reviewable commits with clear messages. Write tests alongside code.
- When a library's current API differs from what the brief assumes, check its docs, then note the change in `docs/decisions/`.
- Ask the owner before adding any dependency that makes network calls, any analytics, or anything that changes the non-negotiables.
- At the end of each phase report: what was built, how to run it, test/eval results, known issues, and questions.
- Ingest articles only with `/ingest-article` (`.claude/commands/ingest-article.md`); `ingest-finish` must report 0 errors. Never edit `corpus/sources/` (snapshots are immutable).
- `eval/questions.real.yaml` is human-written only: never generate, edit, reformat or copy aliases into it (see `eval/REAL_QUESTIONS.md`). Report real and fixture eval results separately.
- Scholar-supplied fields use `<field>_origin: scholar_review` plus an entry in `corpus/reviews/<node-id>.yaml` (who wrote/approved, sha256), only on verified nodes. Never set or fill these yourself; the owner records them with `record-review`.
- `research/` (e.g. `research/munazara/`) is unverified research. It may be imported into **dev builds only**, with `python -m dalail_pipeline import-research research/munazara`, as `origin: gemini-research`, `status: draft` (generated into `corpus/research-import/`, regenerated on every run, never hand-edited, never via `/ingest-article`). `build --prod` refuses any node, alias, counter-question or edge with that origin (validation + post-build scan). Nothing from research is ever shareable; in the app it is shown only behind the "AI-extracted from video — not verified by scholars" banner, and Gemini's "evidence as said" is shown as plain text, never as a dalil card (ADR 0008). Real nodes still come only from scholar articles captured in `corpus/sources/`.
- Sources carry `default_opponent`; ingestion flags claims from another group for the owner, never guesses. Never translate or transliterate article text (Urdu script stays Urdu script).
- Prod builds exclude non-verified nodes and prune follow-up edges to them (reported); citing an unverified hadith or an ayah missing from `corpus/quran/` fails the build.

## Commands

```bash
pnpm install                 # JS/TS workspace (node-linker=hoisted for React Native)
pnpm lint && pnpm typecheck && pnpm test
cd pipeline && uv sync && uv run pytest && uv run ruff check .
bash scripts/ci.sh           # everything CI runs (keyword-only; no model needed)

# corpus pipeline (from pipeline/)
uv sync --extra embed                                   # + llama-cpp-python (compiles, CPU)
uv run python -m dalail_pipeline fetch-model            # pinned e5 GGUF -> models/ (sha256 checked)
uv run python -m dalail_pipeline validate [--prod]
uv run python -m dalail_pipeline build --dev|--prod [--no-embed]
uv run python -m dalail_pipeline stats
uv run python -m dalail_pipeline new-source --url URL | --file PATH --opponent ID [--id ID]
uv run python -m dalail_pipeline record-review --node N --field short_answer --written-by W --approved-by A
uv run python -m dalail_pipeline ingest-finish <source-id>   # spans, cited_in, checks, summary
uv run python -m dalail_pipeline check-verbatim | dedupe | next-id node --topic T | next-id hadith
uv run python -m dalail_pipeline transcribe <audio> --source-id yt-<id>   # dev-only, needs --extra transcribe
python research/munazara/tools/coverage.py [--update-readme]               # transcript coverage audit
uv run python -m dalail_pipeline import-research ../research/munazara        # dev-only research import
uv run python -m dalail_pipeline embed-queries ../eval/questions.fixture.yaml ../eval/questions.real.yaml
pnpm --filter @dalail/eval eval [--mode keyword|hybrid]  # top-1 / top-3 / ambiguous / no-match
pnpm --filter @dalail/mobile android   # dev client on emulator/device (needs Android SDK)
```

In `apps/mobile`, add Expo packages with `npx expo install <pkg>` so versions match the SDK.
